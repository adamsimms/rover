## Naming in applications

| Practice | Why |
|----------|-----|
| Device name **Fielding** may stay out of a given application | Title still open; literary homage cannot be explained publicly until permission ([#23](https://github.com/adamsimms/rover/issues/23)). Prefer *the rover / the device / a machine*. Avoid *instrument*. |
| Prefer short titles in the Cloudberry / Cabin / Driftwood family when a name is needed | Long thesis titles read as grant copy. Artica working title: *Uncertain Field Notes* (placeholder; project title still open). |
| Avoid unexplained folklore names (*Fetch*, etc.) unless the body can carry them | Clever without a gloss costs trust on a short form. |

## Necessity / “why this place”

Hosts that screen for place-specificity (Artica: High Arctic only if required) need **subject as fact**, not a colder lab metaphor.

| Do | Don’t |
|----|-------|
| Lead with one spine (for Artica: emptied purpose + incomplete belonging; migration / displacement as lived parallel) | Numbered stack of “also” / “third reason” essays |
| Fold ethics and practical tests into that spine | Invent climate-science necessity to match a host’s sustainability lede |
| Echo host mission language once if true (e.g. Artica About: migration) | Keyword-stuff or invent geopolitics / minority claims |
| Keep winter / polar-night / gear tests as support or timing | Lead with equipment validation alone |

**Artica-specific spine (resolved for #72):** grandmother resettlement / Pinchard’s Island meets Longyearbyen remaking and emptied extraction sites (e.g. Svea); fourth path = attending after the old life is gone; ethics of machine + camera in a governed, extractive landscape; polar-night edge as practical wake / seeing test timed to returning light / Solfestuka.

## Description craft

- Opening **question hook** can work; the next sentence after any intervening context must bridge (*From those fragments I am building…*), not float (*My response is…*).
- Name **intangible heritage** and real archive *sources* as material the work draws on; never imply licensed training reuse or a formal archive partnership until one exists.
- AI contrast (fluent industry vs fragmentary, borne and safeguarded, open system) is strong when it serves the work, not as a tech rant.
- State the **endgame** (later unattended record on Pinchard’s) and the **residency outcomes** (components, image/text experiments, clearer path) so the host sees a four-week job, not only a concept.
- Prefer `software` over `firmware` in application language.

## Public engagement

Form fields often want **interest / format / benefit**. Hosts that care about give-back (Artica: leave something vs extraction history) need a clear hierarchy, not a menu of offers.

| Prefer | Avoid |
|--------|-------|
| One primary public moment + one timed companion (e.g. talk + festival open studio) | Stacking talk + separate ethics program + studio + coffee club as peers |
| Put guest-practice / ethics *inside* the open studio, not as a second thesis that repeats Why | Restating occupy / permissions / extract triad from the necessity field |
| Leave-behind scoped to **what was made there**, if useful (e.g. copies with host / library) | “All research to the archive” or inventing a deposit agreement |
| Soft asks that match **self-led** residencies (*welcome guidance*) | *I need help organizing…* as if staff run the residency |
| Concrete “shape how it behaves” (what it may photograph / name / stay silent) when inviting collaboration | Vague benefit frames or dual “for the community / for my work” padding |

Informal host networking (e.g. First Friday Coffee Club) is resident hygiene, not a public-engagement deliverable.

## Practical / access

- Tell hosts what they must know: hardware as baggage, **lithium** clearance, outdoor testing, guides beyond a safety zone.
- Printer / introductions / engagement logistics: firm needs in plain language; tone still self-led.
- Access: keep honest and short; do not invent requirements.

## Process pattern (drafts → submissions)

For a heavy call, keep a print-ready answers file separate from the research call file. Those files are scratch, not live status:

- `Sketchpad/residencies/calls/<slug>-application-responses.md`: form-field answers, word counts, notes for artist voice (while drafting)
- `Sketchpad/residencies/calls/<slug>.md` or `<slug>-*.md`: research, guardrails, submit checklist
- On submit: promote into [submissions/](submissions/)<slug>/ (see [submissions/README.md](submissions/README.md)) and dual-write status to the vault Residencies MOC

Do not paste full essays into GitHub Issues. Confirm CV size / page format and portfolio strength before upload.
